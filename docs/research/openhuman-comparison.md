# OpenHuman vs. pi-optchat: Architecture, Footprint, and Adoption Plan

## Executive Summary

**OpenHuman** (`tinyhumansai/openhuman`, v0.64.20) is a GPL-3.0 desktop application (Tauri v2 + React) and embeddable Rust library (`openhuman-core` / `openhuman-embed`) designed to run hundreds of lightweight agents in a single OS process. Its core design bets on compiled Rust in-process concurrency, a frozen KV-cache-friendly prompt + tool catalogue, deterministic/RLM-style tool-output compression with handle-based querying (`TokenJuice` / `TinyJuice`), deferred tool discovery (`Jev` / BM25), and a shared Tokio runtime with SQLite-backed persistence (`TinyStorageDrivers`).

**pi-optchat** (`v0.8.4`) is an always-on TypeScript Pi extension running on Node.js (`>=22.19.0`), built around an **endless zoomable binary summary tree** (`src/memory.ts`, `src/compactor.ts`), a multi-account quota/failover system (`src/quota-health.ts`, `src/wake-route.ts`), a contract-driven worker crew (`src/crew.ts`, `src/agents.ts`), proactive heartbeat + gitwatch wakes (`src/heartbeat.ts`), Slack/WhatsApp bridges (`src/slack-bridge.ts`), and deterministic effect-classification approvals (`src/effect-classifier.ts`, `src/authorization.ts`).

OpenHuman is dramatically lighter in **per-agent process footprint, cold-start latency, and per-turn token overhead** because it runs all agents in one compiled Rust process (~1.7–3.5 MiB marginal RSS per agent vs. spawning Node/Pi subagent sessions) and strips large tool outputs *before* they enter the LLM context (`2 KB` gate + format-aware compressors + handle tools). Conversely, **pi-optchat** is much stronger in **long-horizon lossless conversational memory** (endless zoomable tree with no silent forgetting), **multi-account quota/failover & cache-aware compaction**, **contract-enforced subagent engineering workflows** (git worktrees, `crew accept`, CI/commit guards), and **zero-external-backend autonomy**.

## Why OpenHuman Is So Light (With Evidence)

1. **In-Process Multi-Agent Concurrency (No Per-Agent OS Process or Runtime)**
   - In `docs/gitbooks/en/developing/architecture/README.md:14-47` and `performance.md:10-33`, OpenHuman boots **one** compiled Rust `Runtime` with one Tokio reactor and one 2-thread storage runtime (`storage.md:101`). Each agent is just a derived `CoreContext` (`agent-harness.md:57-64`), costing **1.73–3.36 MiB** marginal RSS (`performance.md:22,129`) vs. ~48 MiB per separate process (`performance.md:30`) or ~184.5 MiB for a Node/tsx Pi session.
   - Idle agents consume **3 ms CPU per 10s** across 500 agents (`performance.md:18-24`).

2. **Strict Dependency-Floor Ratchet & Feature Gating**
   - `scripts/kernel-floor.limits:1-18` enforces a downward-only CI ratchet (`334` packages / `311` unique crates / `3` native builds for the `flows` profile). Heavy subsystems (documents, voice, web3, MCP, desktop control) are either behind Cargo feature flags or loaded lazily as `cdylib` modules over `TinyBus` (`performance.md:63-67`, `architecture/README.md:101-118`). They even deleted `tree-sitter` and `whisper-rs` (`kernel-floor.limits:556-588`) to keep binary and memory footprints small.

3. **TokenJuice: Deterministic Pre-LLM Output Compression & Handle Offloading**
   - Every tool result `>= 2 KB` passes through `ToolOutputMiddleware` (`crates/openhuman-core/src/agent/tinyagents/middleware/tool_output.rs:1-4`) and `TinyJuice` (`docs/gitbooks/en/features/token-compression.md:16-104`).
   - Instead of dumping 20–30 KB of `git status`, `cargo build`, grep hits, or JSON arrays into the prompt, it classifies content into 7 kinds (`Json`, `Diff`, `Html`, `Search`, `Code`, `Log`, `PlainText`) with zero regex on the hot path (`token-compression.md:47`), tabulates JSON arrays, collapses unchanged diff/code blocks, and for `>= 500` tokens stores the original in an in-memory/disk CCR cache (`max 256` entries / `64 MiB`). The model sees a 500-char preview + outline + handle `⟦tj:<hash>⟧` and can query it with `juice_find` (`grep`/`jq`/`bm25`), `juice_extract`, `juice_summarize`, or `juice_retrieve` without any LLM call (`token-compression.md:71-90`).

4. **Frozen KV-Cache Prefix Contract (Tools + System Prompt + Append-Only History)**
   - `crates/openhuman-core/src/prompts/composition.rs:72-120` and `agent-harness.md:165-200` separate `Stable`/`Context` prompt tiers from `Volatile` content. The system prompt is built **only on turn 1** (`agent-harness.md:165-167`).
   - Tool lists are sorted deterministically (`connected_set_hash`, `agent-harness.md:197`), dynamic memory packs (`MemoryPackMiddleware`, `middleware/memory_pack.rs:1-27`) are injected ephemerally per request and **never written to the transcript**, and `pair_tool_cycles` operates locally so earlier messages never mutate retroactively (`agent-harness.md:198`). This keeps `cached` tokens near `prompt` tokens from turn 2 onward (`agent-observability.md:85,93-97`).

5. **Deferred Tool Discovery (`Jev` / BM25) & Small-Model Trigger Triage**
   - Instead of sending schemas for 50–1,000+ tools on every turn, OpenHuman defers tools behind `tool_search` (`jev.md:40-41`), returning only `top_k = 3` (`jev.md:86`).
   - Incoming webhooks/events are filtered by `trigger_triage` (`crates/openhuman-core/src/triage/decision.rs:15-43`) running on a tiny local model (`gemma3:1b-it-qat`) with lenient JSON parsing, dropping noise before a frontier model is ever invoked.

6. **Backgrounded Post-Turn & Memory Lifecycle**
   - `memory/lifecycle/session_hooks.rs` (`memory.md:10,48-55`) never blocks turn 1 on a remote memory query: `pre_turn` reads a 60s-TTL in-memory prefetch cache immediately and refreshes asynchronously; `post_turn` logs turns and builds beliefs after the user already has their answer (`agent-harness.md:189`).

## What OpenHuman Does That We Don't

1. **Format-Aware Deterministic Compression + Queryable Output Handles (`TokenJuice` + `juice_find`/`juice_extract`)**: Our `OutputContext` (`src/output-context.ts:7-58`) only activates at `>= 8 KB` and only handles `bash`/`powershell`/`grep`/Google Analytics reports with generic head/tail or 5-row truncation, plus raw `output_read`. OpenHuman compresses at `>= 2 KB` across 7 formats (including JSON table-ization, diff lockfile collapsing, HTML-to-text, and code signature collapsing) and gives the model `grep`/`jq`/`bm25` query tools over the cached original.
2. **Ephemeral Per-Turn Memory Injection Without Mutating Prefix**: OpenHuman injects `<memory-context>` ephemerally per request (`memory_pack.rs:5-8`) without touching the frozen system prompt or persisted transcript. In `pi-optchat`, the `<chat>` memory view grows in the prompt and periodically triggers batch merges (`Sawtooth`), which even with `DEFER = 1.5` (`src/memory.ts:9`) eventually invalidates the prefix cache.
3. **Zero-Cost / Local-LLM Trigger Triage (`drop | acknowledge | react | escalate`)**: OpenHuman routes external triggers through a tiny local model (`triage/decision.rs:1-43`) before waking an expensive model. Our `heartbeat.ts` (`HEARTBEAT_PROMPT`) wakes a cloud model on every cadence tick unless `radarDigest` (`heartbeat.ts:119`) is byte-identical.
4. **Loopback Inference Capture Proxy (`pnpm debug capture`)**: OpenHuman has a built-in local HTTP proxy (`agent-observability.md:64-101`) that logs exact wire payloads, `served_by`, `cache_key`, `cached` vs. `prompt` tokens, and non-2xx HTML error bodies—making cache-prefix regressions immediately visible.
5. **Hint-Based Model Routing (`hint:fast`, `hint:summarize`, `hint:burst`)**: OpenHuman decouples call sites from concrete model names via `[[model_routes]]` hints, allowing runtime remapping and local/BYOK/managed mixing without editing code.
6. **Secret & PII Scrubbing on All Memory Writes (`ScrubbingEngine`)**: Every memory write passes through a fail-closed redactor (`memory.md:66`, `security.md:19`).
7. **Rolling Hourly Side-Effect Action Budget (`max_actions_per_hour`)**: Caps autonomous runaway loops even when `AutonomyLevel` is `Full` (`agent-harness.md:181`, `security.md:48`).

## What pi-optchat Does Better

1. **Lossless Endless Zoomable Memory (`Sawtooth` Binary Tree)**: OpenHuman's RAG-based `TinyMemory` (`recall` + `ContextLadder`) can miss chronological context or silently drop older details during summarization. `pi-optchat`'s `src/memory.ts` keeps **every** message addressable forever via `zoom(id, n)` and `search(text)` with strict signpost rules (`SUMMARY_SIGNPOSTS`, `src/prompts.ts:4`) and `foreignIds` / `closedConflicts` hallucination guards (`src/compactor.ts:14-15`).
2. **Multi-Account Quota Awareness, Failover & Graceful Parking**: `pi-optchat` tracks real 5h/7d provider utilization (`src/quota-health.ts`, `src/wake-route.ts`), parks workers cleanly on `QuotaOutage` (`src/quota-hold.ts`), and resumes them when quota resets—something OpenHuman's single-subscription/BYOK router does not model.
3. **Contract-Enforced Engineering Crew & Git Worktree Lifecycle**: `src/crew.ts:87-99` enforces `Goal / Acceptance / Evidence / Authority` contracts before spawning, isolates writers in git worktrees (`scripts/worktree.mjs`), ships via `crew accept` (`src/crew-accept.ts`), and maintains per-project specialist memory trees (`SPECIALIST_VIEW_BYTES = 8192`).
4. **Domain-Specific Engineering Guards**: Pre-execution deterministic guards in `src/index.ts:191-200` (`powershell-quoting.ts`, `bash-timezone.ts`, `bash-recursive-grep.ts`, `commit-hook-guard.ts`, `merge-ci-guard.ts`, `deploy.ts`) prevent real-world Windows/Git/CI footguns with zero LLM round trips.
5. **Zero External Backend Dependency**: `pi-optchat` runs 100% locally on flat files and the user's existing Pi CLI/provider accounts, whereas OpenHuman's default memory/search/OAuth/voice stack assumes a TinyHumans backend or self-hosted CortexDB.
6. **Lean Runtime Footprint & Zero NPM Runtime Dependencies**: `pi-optchat`'s `package.json` has `0` runtime `dependencies` (all 5 peer deps come from Pi), `28.2k` LOC in `src/`, and `232` fast native `node --test` files—far easier to audit and iterate on than OpenHuman's 818k-line Rust + 387k-line TS + 21-submodule monorepo.
