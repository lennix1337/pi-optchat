# Optional assistant inbox (experimental v1)

Standalone Node >=24 package; `npm test` runs the native contract and store tests. SQLite storage is separate from the Node >=22.19 Pi extension. The store does not implement authorization, verification or dispatch. All parsers take `unknown`, throw `TypeError` on invalid input and return the original value, not a sanitized copy. Treat accepted objects as immutable and copy them before retaining across trust boundaries. All fields are required and unknown fields and versions are rejected; identities are nonempty, well-formed Unicode strings, not interchangeable IDs. Exact `.` and `..` task IDs are rejected across task/event/attempt/approval/response boundaries because URL transport normalizes dot segments; other opaque IDs remain unchanged. Malformed persisted data is not silently repaired. Raw source content is not part of these projections. UTC timestamps use four-digit years and `Z`, with either no fractional seconds (for example `2026-10-28T12:00:00Z`) or exactly three milliseconds digits (`2026-10-28T12:00:00.123Z`); dates and times must be real calendar values.

- `src/contracts/events.ts`: `parseEvent`, `parseEventSequence(values, profileId, afterSequence)` and `sourceAuthority`. Events contain profile, session, channel, task and run IDs, nested source (`actorId`, `sourceKind`, `sourceEventId`), event ID, UTC observation time, positive profile-local sequence, correlation ID and an observed evidence reference. A sequence batch must be contiguous immediately after the nonnegative cursor and belong to the supplied profile. An empty batch is valid. Deduplication by event/source ID is a store responsibility.
- Authority table: `trusted-local-human` → `human_intent`; `external`, `worker`, `model` → `untrusted`; unknown kinds fail. This is a classification of *already authenticated provenance*, never proof that caller-supplied metadata is authentic and never an effect grant. The transport must establish provenance independently. An observed reference is not a verified result.
- `src/contracts/tasks.ts`: `parseTask`, `parseAttempt`, `assertTaskTransition(task, next, profileId, expectedRevision)`, `parseTaskResponse(response, currentTask)`. Tasks require a nonempty title: caller-minimized display metadata for list/detail, not raw external content or a new authority source. Tasks also contain status, independent verification (`verified`, `not_verified`, `blocked`), positive task and input revisions and event source reference. `resolved` does not imply success or verification. Attempts represent `planned`, `claimed`, `running`, `effect_uncertain`, `reconciled`, `finished`; the parser alone does not authorize attempt transitions or retries. Responses require the current `needs_input` task and matching profile, task, task revision and input revision.
- Transition graph: suggested → queued/cancelled/resolved; queued → working/cancelled; working → needs_input/ready_for_review/succeeded/failed/cancelled; needs_input → working/cancelled; ready_for_review → working/succeeded/failed/cancelled/resolved; succeeded → resolved; failed → queued/resolved; cancelled → resolved; resolved has no outgoing transitions. This is a v1 contract, not proof of a real-world outcome.
- `src/contracts/approvals.ts`: `parseApproval` accepts a one-use request binding profile, task, run, account, effect, destination, content hash, expiry, policy version and owner. It neither checks expiry against a clock nor grants or consumes authority. Persistent policy changes are not execution-button scopes.
- `src/contracts/connectors.ts`: `parseConnector` captures profile/account/server, schema hash, explicit granted capability names, secret reference and `read`/`write`/`unknown` effect. Unknown is not read permission; names and hashes are opaque claims, not validated schemas, secrets or grants.
- `src/contracts/artifacts.ts`: `parseArtifact` captures profile, owner, type, artifact version, hash, producer, location, provenance and review state. HTML and locations remain untrusted; parsing does not make them safe to render or access.

## SQLite task store

`src/store/db.ts` exports `TaskStore(path, profileId)`, bound to one profile for its lifetime:

- `create(task, event)`, `transition(taskId, expectedRevision, nextStatus, event)`, `respond(response, event)` return detached task snapshots. Each write uses one immediate transaction for the event, task projection and any private response. Caller-supplied event sequence must be the next contiguous sequence in that profile; duplicate event/source/task identities and stale revisions refuse without partial writes.
- `get(taskId)` returns a task or `null`; `list(cursor = null, limit = 50)` returns `{tasks,nextCursor}` in opaque task-ID order. `events(afterSequence = 0, limit = 50)` returns `{event,operation,task}` records in sequence order. Limits are 1–100. Reads do not resolve tasks or consume approvals. Replaying snapshots reconstructs the task projection, not private responses or execution state.
- `close()` releases the database. Opening a new store migrates an empty database transactionally using `user_version`; newer versions and unknown unversioned tables refuse. File-backed reopen preserves tasks and event references.

Raw answers are stored in a separate `responses` table and omitted from task/event reads; the SQLite file is private runtime data, not encrypted secret storage. Keep it outside Git. Entering `needs_input` advances `inputRevision`; responding compares both revisions and advances metadata to `working`. Neither that transition nor a submitted answer dispatches work or grants effects. A `succeeded` status still has `not_verified` verification: independently observed outcomes are not established by caller claims. Uncertain external effects require reconciliation before retries; no exactly-once external delivery is implied.

## Manual operation (explicit opt-in)

Nothing starts on installation, import or `/reload`. This package is not a daemon or task executor. In the installed package/check-out directory, inspect `node assistant/src/main.ts --help` first. An operator who authorizes a local service supplies two private JSON files outside version control:

Server config (absolute paths for the config argument and database; choose an unused local port):

```json
{"version":1,"profileId":"work","databasePath":"C:/private-runtime/work/tasks.sqlite","endpoint":"http://127.0.0.1:49761","token":"<operator-generated-random-token>"}
```

Client config, at `~/.optchat/profiles/work/assistant.json`:

```json
{"version":1,"profileId":"work","endpoint":"http://127.0.0.1:49761","token":"<same-random-token>"}
```

Use a cryptographically random token (at least 32 random bytes encoded as hex); never place the actual value in a CLI argument, committed file, chat or logs. The literal examples are placeholders, not credentials. Restrict both files and the SQLite directory to the operating-system user. Before reading the server config or opening SQLite, the manual entry point refuses linked paths, hard-linked files, unsafe ownership and nonprivate runtime permissions; it does not repair permissions or create missing parent directories. Windows inspection requires the installed PowerShell 7 at `C:/Program Files/PowerShell/7/pwsh.exe`, and refuses grants or ownership outside the current user, SYSTEM and Administrators. POSIX runtime directories require mode 0700 and database/sidecar files must be owner-only. The config remains inside its owner-only directory. Checks assume quiescent, user-controlled directories, not protection against concurrent path replacement or a privileged administrator. The low-level `TaskStore` caller must establish privacy itself. Client config permissions remain the operator's responsibility; the Node 22 client does not import the standalone ACL checker. The database is not encrypted. POSIX users replace the example Windows path with their own absolute path.

After authorization, start manually with `node assistant/src/main.ts --config <absolute-config-path>`. The server binds only `127.0.0.1`, reports safe readiness, and refuses address collisions without retry. Stop with Ctrl+C. POSIX shutdown closes connections within a bounded deadline; Windows child-process termination tests prove persistence/restart, not graceful signal delivery. No scheduled task or system service is installed. Removing the client config disables future command requests; stop the separate process explicitly. Profile changes/reloads cannot launch it or resend task responses.

The active profile reads its client config only on an explicit `/assistant` command. See the [discovery skill](../skills/personal-assistant/SKILL.md) for commands. This version has no model-facing write tool or task-creation command: a trusted local producer must use the authenticated metadata API below. Existing approvals, operations and agents remain in their original journals. `/assistant local [cursor]` pages their current-session metadata (external agents are profile-scoped), with exact operation/agent references and safe approval metadata; `/assistant list` includes the first local page even without service configuration. Reading neither consumes grants nor reconciles outcomes; approval tokens, arguments, reports and private evidence stay with their source owners. These journals are not automatically ingested as mutable task records; suggestions use the service’s explicit `suggested` task status.

## HTTP boundary

`createAssistantServer({store,token,profileId,onError?})` returns an **unlistened** Node HTTP server. The profile must match the bound `TaskStore`. `nextSequence()` and `matchesProfile()` are read-only store accessors; sequence admission is still rechecked inside each write transaction. HTTP requests carry `Authorization: Bearer <token>`; browser Origin headers and non-allowlisted remote addresses refuse. No CORS or proxy support is enabled. The client only accepts a literal `http://127.0.0.1:<port>` endpoint and refuses redirects.

- `GET /v1/tasks?cursor=<opaque>&limit=50` → `{tasks,nextCursor}`; `GET /v1/tasks/<encodedId>` → task.
- `GET /v1/events?after=0&limit=50` → stored event records; page sizes are 1–100. Sequence is profile-local, not task-local.
- `POST /v1/tasks` → `{task,context}`; `POST /v1/tasks/<encodedId>/transition` → `{expectedRevision,nextStatus,context}`; `POST /v1/tasks/<encodedId>/respond` → `{response,context}`.

Here arrows on POST describe the **request** body. Successful POST responses are the updated task. `context` is exactly `{sessionId,channelId,runId,sourceEventId,evidenceReference}`; unknown fields refuse. Create uses a version-1 queued/suggested task at revision/inputRevision 1, verification `not_verified`, and matching source event ID. Responses use `{version:1,profileId,taskId,revision,inputRevision,text}`. The server assigns event identity, time, sequence and **model** provenance; caller labels can never authenticate human authority. A same-profile original reference is `optchat:<URL-encoded-profile>:<original-message-id>`; it is still an unverified historical source.

Status codes: success 200, malformed request 400, bad token 401, Origin/remote refusal 403, missing route/task GET 404, stale/replayed/invalid transition 409, unexpected failure 500. POST errors do not disclose stored private input. Bodies over 64 KiB or inactive for 2 seconds / unfinished after 5 seconds can close the transport instead of returning JSON. The client bounds responses to 256 KiB and waits at most 5 seconds; a failed write is uncertain, not safe to resend. Unexpected internal failures emit one safe category through `onError`, or a bounded generic diagnostic by default, without raw error/input details.

## Effect policy foundation (T02, host-only)

Nothing here is a model tool, HTTP endpoint or shell sandbox; native Pi tool calls stay governed by OptChat's existing effect approvals. `src/policy/` is the boundary future connector/browser/channel adapters must dispatch through:

- `inspectEgress(bytes, knownSecrets)` scans exact UTF-8 bytes. A host-supplied known secret anywhere → `deny`; likely card numbers, credential key/value pairs, SSN-style identifiers, malformed UTF-8 or input over 1 MiB → `review`. Heuristic only: it misses semantic PII and flags some benign text. Reasons are codes, never matched values.
- `createGateway({databasePath, profileId, operatorAuthority, policy, inspect})` keeps its own private SQLite file (not the task store). `prepare(request)` snapshots the request once (plain data only; accessors and non-plain objects refuse) and binds profile, session, task, run, adapter, action, account, destination, policy version, expiry and a payload digest; it stores digests and states, never payload or authority. `decide(reviewId, 'approve'|'deny', authority, rule?)` accepts only the exact host-owned authority object; a field such as `source: 'operator'`, a bearer token, task response or email content is not authority. Approval is once by default; an explicit `{scope:'rule', uses ≤ 100, expiresAt}` reuses the same exact binding for distinct operation IDs and is never renewed by reopen. A sensitive-content `deny` or policy `deny` cannot be approved away.
- `dispatch(request, invoke)` re-runs policy and inspection under `BEGIN IMMEDIATE`, conditionally consumes the grant and records a durable intent before calling `invoke(bytes, metadata)`. Adapters must deliver using those two arguments, which are owned copies of the approved snapshot, not the caller's request. A thrown sink or a failed result write returns the fixed `effect_uncertain`; the intent stays uncertain and the same operation ID is refused until independently reconciled. A returned response is `response_recorded`, not verified. Two connections or processes cannot spend one grant (tested against a quiescent private database).
- Root `src/assistant-policy.ts` `createAssistantPolicy` is the host wiring: a trusted adapter registry, the profile's `autonomy.json` decided through the same `readProfileEffectPolicy` as native hooks (`free`/`report` run, `report` is logged without payload, anything else needs review), and `inspectEgress`. Unknown adapters, mismatched accounts/destinations or a stale policy version deny. No adapter is registered by default and no real account is connected.
- `src/assistant-review.ts` `registerAssistantReview(pi, policy, authority)` adds `/assistant-review`. The host passes the same authority object it gave the policy, and nothing else holds it. `list` shows each pending review's exact adapter/action/account/destination, expiry, flagged reason codes and whole content with terminal controls escaped. `approve <reviewId>` runs only in interactive TUI mode, only for content that fits whole on screen (≤4000 escaped characters, valid UTF-8), and only after `ctx.ui.confirm`; `deny` is final. Pending exact bytes live in host memory only, so after reload the producer must prepare again; the durable grant table never gains anything from a reload.

Effect paths today, and what governs each:

| Path | Effect | Governed by |
| --- | --- | --- |
| Native Pi tools (bash, write, edit, subagent, shell_start, codemode...) | anything the tool does | OptChat effect approvals (opt-in: `OPTCHAT_EFFECT_APPROVALS=1|risk`) + `autonomy.json` + uncertain-operation journal. Off by default: then only the journal fences replays. Not a sandbox. |
| Assistant HTTP API / `/assistant respond` | task metadata and private responses in SQLite | bearer + loopback + profile; never dispatches work or grants effects |
| Manual service entry `assistant/src/main.ts` | binds 127.0.0.1, writes its SQLite | explicit operator start; privacy checks before opening files |
| Worker `effect` jobs (T03), routines (T04, via worker), vault injection sinks (T05), future connectors, browser, channels (T06-T13) | external sends/mutations | must call `createAssistantPolicy().dispatch`; an adapter that invokes outside it is a defect |


## Durable worker and notification outbox (T03, library only)

`src/runtime/worker.ts` `createRuntime` runs jobs in a process separate from the TUI. Nothing starts it automatically: service install and autostart belong to T13.

- One owner holds a SQLite lease. Every owner write commits only while its lease token is current, so an owner that lost the lease after expiry gets `lease_lost` and changes nothing. Producers (TUI, HTTP) open the same database to `enqueue`, `cancel`, `notify` and read without taking the lease.
- Internal job kinds must be idempotent: after a crash, `running` jobs are requeued up to `maxAttempts`, then `failed` with `attempts_exhausted`. Enqueueing the same ID with the same input is a no-op; different input is `job_conflict`; a full queue is `queue_full`.
- The `effect` kind dispatches only through the T02 gateway. The job is marked `dispatching` before the gateway records its intent; recovery asks `gateway.status`: `absent` requeues, `response_recorded` completes, `uncertain` becomes `effect_uncertain` and is never sent again. An adapter's optional `reconcile` may observe the external system and mark it `done`; it must never resend. `approval_required` leaves the job `blocked`.
- `cancel` stops queued jobs at once and running ones at their next boundary; a dispatched effect cannot be recalled. `stop` refuses new jobs, children and effects, aborts handlers, requeues interrupted work and releases the lease.
- `notify(id, channels, body)` stores one row per channel under a stable ID; `deliver(channel, send)` is at-least-once (a crash between send and acknowledgement resends the same ID, so channels deduplicate by ID). Failures keep a minimized `delivery_failed` diagnostic and become `failed` after `maxAttempts`, still listed by `notifications()`.
- Effect inputs, including the payload, are stored in the runtime database: keep it under the same private-directory rules as the task store.

## Routines (T04, library only)

`src/routines/manager.ts` `createRoutines({ databasePath, runtime })` schedules jobs on the T03 worker; it never runs work or effects itself, and effects inside a routine job still need gateway grants. Call `tick()` from the host loop; nothing ticks automatically.

- A routine is bound to a profile, a handler kind, a capability list and an authorization reference, all passed to the job input. It is created **paused** (`not_activated`); `resume(id, operator)` activates it and schedules from now, so time spent paused is never "missed". Changing kind, profile, capabilities or authorization pauses it again (`needs_reactivation`); changing only time or input keeps it active.
- Schedules (`src/routines/schedule.ts`): `daily`/`weekly` at a local `HH:MM` in an IANA zone, or `interval` minutes from an anchor. A time skipped by a DST gap runs one gap later; a time repeated by a fold runs once. Each occurrence has a slot key (local date and time) and its job ID is `routine:<id>:<slot>`.
- Missed time (sleep, restart, clock jump): `missed: 'once'` (default) runs one consolidated job for the newest slot, with `missed` = how many earlier slots were skipped; `'skip'` runs it only within `graceMs`, else records `skipped_missed`. Missed slots are never replayed one by one.
- A clock that moves backwards fires nothing and records `clock_skew`. Several schedulers on one database claim each slot once (the claim commits before the enqueue; an interrupted claim is completed by the next tick with the same job ID). A slot key that already ran never runs again, even after a time-zone edit.
- No overlap: a slot due while the previous job is unfinished records `skipped_overlap`. A full worker queue keeps the claim and retries. `maxFailures` consecutive failures pause it (`consecutive_failures`); an `effect_uncertain` job pauses it at once (`effect_uncertain`) for reconciliation. `get`/`list` show state, reason, `nextRunAt` and failures; `history` lists runs newest first.
- `adopt()` imports an existing wake or dream as a paused routine with no capabilities and no authorization: its old permissions do not carry over, and it does not run until an operator re-grants and activates it. The existing OptChat wakes and `optchat-dream` task are not changed by this library.

## Secret vault (T05, library + operator command)

`src/secrets/vault.ts` stores secrets that can be injected but never read back. There is no method that returns a value.

- Each value is sealed with AES-256-GCM (`node:crypto`). The 32-byte data key is wrapped by `src/secrets/protector.ts` `osKeyProtector()`: on Windows that is DPAPI for the current user, and only the wrapped blob is stored. Other platforms have no dependency-free OS keystore here, so `Vault.open` refuses (`vault_unavailable`) rather than keep a key beside the data. The database must pass the same owner-only privacy check as the task store, and `secure_delete` zeroes freed pages.
- `put(value, { profileId, origin, action }, expiresAt?)` returns a random `sec_…` reference. The origin must be an exact `https://` origin (or `http://` loopback), with no path or credentials. The ciphertext's associated data binds the reference, profile, origin and action, so copying it to another row fails authentication.
- `inject(ref, binding, sink)` decrypts only for the exact binding, hands the bytes to `sink` (the consented destination's adapter), then wipes the buffer. A changed origin, action or profile is `binding_mismatch` before decryption. A sink failure is `injection_failed`, without its message. Errors carry only a code.
- `rotate` overwrites the value. `revoke` is final and erases the ciphertext. `purge` deletes revoked and expired (ephemeral) references.
- `src/assistant-secret.ts` `registerAssistantSecrets(pi, source)` adds `/assistant-secret [list | add <origin> <action> | rotate <ref> | revoke <ref>]`. Values are typed or pasted into a masked dialog in the interactive terminal only. They are not echoed or copied, and they never reach the model, the session, notices or RPC. Only the reference is shown. JavaScript strings cannot be wiped, so typed characters live in memory until the dialog closes.
- Limits: the vault ends at the sink. No browser or shell injection exists yet. T06 must keep a page, DOM, shell or artifact from reading an injected value back; until then, browser injection stays blocked. Nothing registers the vault or the command by default.

## Isolated computer and human takeover (T06, library only; browser blocked)

`src/computer/manager.ts` `createComputers()` gives each (owner, profile, agent) its own disposable Linux container on the local Docker engine. `src/computer/docker.ts` `probeDocker(image)` reports whether the engine runs with seccomp and has the image; nothing is ever pulled (`--pull never`), so a missing image is `computer_image_missing`.

- Container: `--network none`, read-only root filesystem, all capabilities dropped, `no-new-privileges`, user 1000, private IPC, pid/memory/CPU limits, tmpfs `/work` (0700) and `/tmp` (noexec). No host mount, no Docker socket, no published port. Each container is labelled with its owner, and only this owner's containers are created, stopped or removed; `cleanup()` also removes ones a crashed process left behind and re-checks each label before removing.
- `exec` runs argv (never a host shell) as user 1000 with an in-container `timeout -s KILL`, so a stuck command dies inside the computer, not only in the CLI. Output is clipped.
- State is in SQLite, so every process sees it. `pause`/`resume` (operator only), TTL expiry refuses work, and `sweep()` destroys expired computers.
- Takeover (operator authority) returns the `docker exec -it` argv for a login or 2FA (with `HISTFILE=/dev/null`). Until `handBack`, agent `exec`, `capture` and `runShell` are refused in every process with `computer_human_control`, and `sweep` keeps the computer even when it has expired.
- `src/computer/effects.ts` `runShell` admits the computer before `gateway.dispatch`: a refusal records no intent, and a sink failure after admission is `effect_uncertain`. `navigate` refuses non-http(s), credentials in the URL, internal, loopback, link-local/metadata and IPv4-mapped targets, DNS answers that resolve inside, and ungranted origins (`src/computer/network.ts`).
- Blocked: no browser is provisioned inside a computer. An admitted navigation fails closed with `computer_browser_unprovisioned` and never falls back to a host browser. Provisioning needs an image with Chromium and `agent-browser` plus a granted egress path, which means downloading an image: that waits for the operator. Until then the vault's browser injection (T05) stays blocked and the network stays off.
- The `assistant-computer` check needs a running Docker engine and `node:22.23.4-alpine3.23` already present. A filesystem-isolated container alone does not prove complete isolation; the tests cover A/B and host canaries, network, mounts, capabilities and root.

## Governed MCP connectors (T08, library only)

- `connectors/mcp.ts` `ConnectorRegistry` discovers an MCP server's tools page by page (bounded pages, cursor loops and duplicate names refused, catalog replaced atomically) and lists them with stable ids `<serverId>/<tool>` in id order. The catalog is never permission.
- A grant names profile, agent, account and tool, has an expiry, and may carry a resource scope (`{ argument, allowed }`, e.g. consented Drive file ids or Notion page ids). It pins the tool's schema hash (input schema + annotations) and the identity of the server that answered; a changed schema, a changed effect claim or a different server behind the same id refuses the call (`connector_revalidation_required` / `connector_replaced`) until the operator grants again. Grant and revoke need the operator authority object.
- Every check runs before the server is called. Tools annotated read-only (and not destructive) are called directly; anything else, including unannotated tools, goes through the T02 gateway: `previewWrite` returns the exact arguments for review, `call` with a write context dispatches once.
- `connectors/stdio.ts` is a minimal MCP stdio client (no shell; the server gets only `PATH`, `SystemRoot`, `TEMP`, `TMP` and the variables the operator lists). Existing servers (Drive, Notion, others) are reused through it; there is no Composio/CopilotKit dependency and no built-in Drive/Notion preset, because the real servers' tool names are unverified until an account is connected (blocked, needs consent).
- Check `assistant-connectors` runs against a disposable local fixture server (`test/mcp-fixture-server.mjs`); it is not proof against a live Drive or Notion account.

## Verification

Use disposable databases only. Root `.pi/checks.json` exposes focused contract, store, mutation, HTTP, manual entry, client, native runtime and source-typecheck recipes; the Pi checks tool requires the repository root, not this nested package. Tests do not activate a personal service, use real credentials or invoke a provider. Installed-runtime checks are isolated temporary sessions; they do not prove live-user activation or every terminal/browser integration. The extension's existing Node 22 CI and standalone Node 24 service are separate compatibility boundaries.
